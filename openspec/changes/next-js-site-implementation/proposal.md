## Why

The visitor-facing app (`site/`) is a Nuxt 4 static rendition that only works as a client-side takeover of a PHP-rendered shell on the WordPress host — it cannot be deployed as a standalone frontend, and operators who want a headless, server-rendered Node frontend (Next.js, Tailwind v4, shadcn/ui) have nothing to adopt. The theme's `progressnow/v1` REST API, zod contracts, JSON fixtures, and design tokens already exist and are dual-asserted, so a second frontend can be built against them with no new backend surface — and the PHP/Timber theme stays the server-rendered option for installs that do not want a Node frontend at all.

## What Changes

- **New `next-js/` app — a headless, Node-hosted Next.js frontend.** App Router, React Server Components, Tailwind v4, shadcn/ui (`new-york`, lucide), TypeScript strict. It runs on its own origin; WordPress is CMS + API only. Every public route kind the Nuxt app renders (`front`, `posts_index` incl. `/blog/page/N/`, `/category/{slug}/`, `?s=`, `page`, `about`, `get_involved`, `calendar`, `post`, `event`, `styleguide`, 404) is served in both languages with `/es/` paths mirroring Polylang 1:1. Search, filtered/paged archives, and calendar windows are **server-rendered** (no client fetch on first paint); later calendar/archive interactions go through same-origin Next route handlers — the browser never calls WordPress directly, so no CORS or REST exposure changes.
- **Data layer on `progressnow/v1`, unchanged.** Server-side fetches validate every envelope against the shared zod contracts (throw in dev, error state in prod), cache with Next's data cache tagged by content, and honor the API's ETag. Internal links from envelopes are path-ified onto the Next origin; images are served through `next/image` with a remote-pattern allowlist for the WordPress uploads host.
- **Incremental revalidation driven by WordPress.** The existing `webhook` rebuild transport (signed `X-Chapter-Timestamp` / `X-Chapter-Signature`, expects `202 { buildId, status }`) targets a Next route handler that verifies the HMAC + replay window, revalidates the content tag, and optionally posts the signed `/build-status` callback. Editors get fresh pages within the dispatcher's debounce; no `node` on the WordPress host, no full rebuild.
- **Canonical ownership is explicit.** A configurable canonical origin (`CHAPTER_CANONICAL_ORIGIN`, default: site URL) is honored by `inc/seo.php` so the `seo.canonical`, `hreflang`, and `og:url` values in every envelope — and in the PHP theme's own `<head>` — point at whichever frontend the operator makes primary. Both frontends agree by construction; the PHP theme remains fully crawlable when it is the primary.
- **Accessibility as a first-class capability.** Parity with the a11y widget (text size, high contrast, reduce motion; `chapter-a11y` storage key with the legacy-key migration), plus skip links, focus management and route announcements on client navigation, reduced-motion-aware view transitions, keyboard-complete calendar/dialog/menu, and axe-clean routes (WCAG 2.2 AA target) asserted in CI.
- **Design system shared with the theme, not copied by hand.** `tailwind.css` tokens, `schemas.ts`, and `categories.json` are consumed verbatim with drift tests against the theme's `src/` (the same mechanism `site/` uses); fonts load by absolute URL from the theme's `static/fonts/`. Components are reimplemented in React + shadcn/ui with visual parity to the current build; the styleguide route is ported (noindex) as the parity surface.
- **Test-driven from the first task.** Vitest + React Testing Library (jest-dom, user-event) for units and components; fixture contract tests reading the theme's `tests/fixtures`; Playwright + `@axe-core/playwright` route e2e against a fixture-backed mock API (the Next equivalent of the nitro mock); a `next-js` CI job (lint, typecheck, unit, e2e, `next build`). Every task lands its tests before its implementation.
- **Portable deployment.** `output: 'standalone'`, a Dockerfile, a health endpoint, and a documented env contract (`WP_API_BASE`, `NEXT_PUBLIC_SITE_ORIGIN`, `CHAPTER_REBUILD_SECRET`, …). Works unchanged on Vercel, a container platform, or a VPS; `docs/deployment.md` gains a "Headless Next.js" section alongside the static Nuxt path.
- **BREAKING: `site/` is renamed to `nuxt-js/`.** The Nuxt 4 app is kept intact; every reference (`README.md`, `docs/deployment.md`, `.github/workflows/*`, `inc/shell.php` static-dir defaults, `bin/worktree-bootstrap.sh`, the CI job, openspec docs) is updated. Existing checkouts, CI variables, and any operator scripts pointing at `site/` must be re-pointed.
- **Not in scope:** editor preview / draft rendering, comments, wp/v2 consumption, replacing or removing the PHP theme or the Nuxt app, running the Nuxt shell handoff and Next on one install simultaneously, provisioning hosting (reference Dockerfile + docs only), and the ICS feed (stays on WordPress; Next links out).

## Capabilities

### New Capabilities
- `next-headless-site`: the Next.js application — route parity with WordPress permalinks in both languages, server rendering of every route kind incl. search/filter/paged/calendar states, `progressnow/v1` data layer with contract validation and tagged caching, envelope-driven SEO head, link path-ification, `next/image` for WP media, 404/error surfaces, styleguide (noindex), ICS link-out, no browser→WordPress calls.
- `next-revalidation-receiver`: the signed webhook receiver contract (HMAC + timestamp window, replay rejection, `202 { buildId, status }`), tag-based revalidation, optional signed `/build-status` callback, health endpoint, and failure behavior (stale-but-served).
- `next-accessibility`: a11y settings parity and persistence, skip links, focus/announcement on navigation, reduced-motion handling, keyboard and screen-reader contracts for calendar/dialogs/menus/accordions, axe-clean routes with WCAG 2.2 AA as the acceptance bar.
- `next-design-system`: Tailwind v4 token sharing with drift guard, shadcn/ui component set (React) mapped from the shadcn-vue set, `data-tone` bands, radius/typography scale, font loading, visual-parity rules and the styleguide parity surface.
- `next-test-harness`: Vitest + RTL setup, fixture contract tests, drift tests (`schemas.ts`, `tailwind.css`, `categories.json`), fixture-backed mock API, Playwright + axe e2e, coverage expectations, CI job, TDD ordering rule.
- `next-deployment`: standalone build, Dockerfile, env contract, health/readiness, caching headers, image remote patterns, deployment guide section, portability guarantees (Vercel / container / VPS).

### Modified Capabilities
- `contract-governance`: the single contract definition must be consumable by three sides (theme, `nuxt-js`, `next-js`); drift tests and dual-sided fixture tests extend to the Next app; fixtures stay theme-owned.
- `seo-metadata`: canonical, `hreflang`, and `og:url` are emitted against a configurable canonical origin (default site URL) instead of the WordPress site URL unconditionally, so a headless primary frontend does not create duplicate-content ambiguity.

## Impact

- **New `next-js/`**: Next.js (App Router), React 19, Tailwind v4, shadcn/ui, zod, Vitest/RTL, Playwright/axe, ESLint (`eslint-plugin-jsx-a11y`), Prettier. Owned by the front-end team.
- **Renamed `site/` → `nuxt-js/`** (`git mv`; contents unchanged): touches `README.md`, `docs/deployment.md`, `.github/workflows/rebuild-site.yml` + `ci.yml`, `wp-content/themes/progressnow/inc/shell.php` (default `CHAPTER_STATIC_DIR` hint), `bin/worktree-bootstrap.sh`, and the pending `nuxt4-static-platform` change docs.
- **Theme (`wp-content/themes/progressnow`)**: `inc/seo.php` reads `CHAPTER_CANONICAL_ORIGIN`; `tests/test-seo.php` + `test-contracts.php` fixtures updated for the origin. `inc/rest.php` and `inc/rebuild.php` are **unchanged** — the `webhook` transport and `/build-status` callback are consumed as-is. `src/**` drift guards gain a second consumer.
- **CI**: new `next-js` job (lint, typecheck, unit, e2e against the mock, `next build`); existing `site` job renamed `nuxt-js`.
- **Docs**: `docs/deployment.md` "Headless Next.js" section; `docs/accessibility-statement.md` lists the Next frontend; root `README.md` describes the three frontends (PHP, `nuxt-js`, `next-js`) and how an install picks one.
- **Runtime/hosting**: a Node 22 host for `next-js` with outbound HTTPS to WordPress; WordPress needs outbound HTTPS to the Next origin (`CHAPTER_REBUILD_TRANSPORT=webhook`). One rebuild transport per install: an install running Next uses `webhook`; the `github` transport remains for the static Nuxt path.
- **Coordination**: `nuxt4-static-platform` (51/59 tasks) must not be blocked — the rename is mechanical and its remaining cleanup tasks apply to `nuxt-js/`. Pending `security-*` changes: the receiver honors the same HMAC scheme and rate/size limits apply to `/build-status`; CSP work in `security-headers-and-cicd-gates` covers the PHP theme only — the Next app ships its own CSP/headers under `next-deployment`.
