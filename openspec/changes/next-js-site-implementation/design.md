## Context

The repo is a WordPress docroot with one theme (`wp-content/themes/progressnow`) and one visitor-facing app, `site/` — a Nuxt 4 static rendition that only exists as a client-side takeover of a PHP-rendered shell (`nuxt4-static-platform`, D1–D5). Everything a second frontend needs already exists on the backend: a first-party read API (`/wp-json/progressnow/v1`: `/site`, `/routes`, `/front-page`, `/pages/{path}`, `/posts[?s&category&page]`, `/posts/{slug}`, `/events`, `/events/{slug}`, `/categories`; transient + ETag cached, content-version invalidated), zod contracts (`src/lib/schemas.ts`) dual-asserted against committed PHP fixtures (`tests/fixtures/*.json`), a `seo` block on every route payload, a Tailwind v4 token sheet (`src/css/tailwind.css`) shared by drift test, a categories registry (`categories.json`), and a signed rebuild dispatcher (`inc/rebuild.php`: `webhook` transport = HMAC-SHA256 over `timestamp.body`, ±300 s window, expects `202 { buildId, status }`; optional signed `POST /build-status` callback that marks a build live and purges the page cache).

What the Nuxt app teaches about the domain, and what this design inherits verbatim:

- **Route resolution is manifest-driven, not filesystem-driven.** `lib/chapter/routes.ts` resolves any path (both languages) against `/routes` (`kind ∈ front | posts_index | page | about | get_involved | calendar | styleguide | post | event`, plus derived `search` / `not_found`), maps `/blog/page/N/`, `/category/{slug}/`, `?s=`, `?category=`, `?paged=` onto the posts index, and decides language by longest front-route prefix. It is framework-free and unit-tested — it ports to Next unchanged.
- **Envelopes carry absolute WordPress URLs** (`homeUrl`, permalinks, `languages[].url`, nav hrefs, `seo.canonical`, `hreflang[].href`, image `src`). Nuxt ran on the same origin so it never had to re-home them; Next runs on its own origin and must.
- **Interactive surfaces are two:** `BlogArchive` (debounced, abortable search/filter/page with URL state) and `EventCalendar` (month/list view, month navigation, windowed events fetch). Everything else is content + chrome (header with mobile nav, language toggle, footer, a11y widget: text size / high contrast / reduce motion persisted under `chapter-a11y` with a one-time `rgv-dsa-a11y` migration).
- **shadcn-vue is built on reka-ui, the Vue port of Radix.** shadcn/ui on Radix therefore carries the same keyboard and ARIA contracts (Popover, Dialog, Accordion, Collapsible, …) — a11y parity of the primitives is by construction; only the composed components need re-verification.
- **Copy is data.** Every visible string comes from `/site.strings` (`nav_*`, `blog_*`, `cal_*`, `event_*`, `nf_*`, `skip_link`, …) or from ACF-backed envelopes; the app hardcodes nothing visible.

Constraints:

- The PHP theme and the Nuxt app keep working unchanged; the only PHP edit is a configurable canonical origin in `inc/seo.php`. No REST or dispatcher changes.
- Headless, Node-hosted, portable (Vercel / container / VPS); no `node` on the WordPress host; WordPress needs only outbound HTTPS to the Next origin.
- Tailwind v4 + shadcn/ui, WCAG 2.2 AA, TDD (tests land before implementation, per task).
- The pending `security-*` changes must not be contradicted: the receiver reuses their HMAC scheme and size limits; the Next app ships its own CSP.
- The Nuxt change (`nuxt4-static-platform`, 51/59 tasks) is still open; the `site/` → `nuxt-js/` rename must be mechanical so its remaining tasks re-point trivially.

Stakeholders: front-end team (owns `next-js/`), backend (one `inc/seo.php` change + fixture update), chapter editors (no new workflow — "Rebuild now" and content saves already dispatch), the operator who chooses PHP / `nuxt-js` / `next-js` per install.

## Goals / Non-Goals

**Goals:**
- Functional and visual parity with the Nuxt rendition for every route kind, both languages, including search/filter/paged archives and the calendar — server-rendered on first paint.
- Zero browser→WordPress traffic: the WordPress origin is a server-side dependency only.
- Fresh content within the dispatcher's debounce via push revalidation; no full rebuilds; correct (stale-but-served) behavior when the receiver or WordPress is down.
- Accessibility as an acceptance bar, not a pass: axe-core-clean routes (run against the production build) in both languages and in every a11y-widget mode, keyboard-complete interactions, honest focus/announcement on navigation.
- Contracts, tokens, and category palette shared with the theme by drift test — the Next app cannot silently diverge.
- One-command local dev against a fixture-backed mock; the whole test suite (unit, component, e2e) runs in CI without WordPress.

**Non-Goals:**
- Editor preview / drafts, comments, `wp/v2`, authenticated states.
- Replacing or removing the PHP theme or the Nuxt app; running Next and the Nuxt shell handoff on one install at the same time (one rebuild transport per install).
- Provisioning or operating hosting; multi-region / multi-instance cache coordination beyond documenting the seam.
- Pixel-diff visual regression (opt-in later; v1 uses the styleguide route + screenshots as review artifacts).
- ICS feed generation (WordPress keeps `/feed/chapter-events/`; Next links out).

## Decisions

### D1. Runtime model: App Router, server components, Cache Components with tag-driven revalidation
`next-js/` is a Next.js 16 App Router app (pinned major; Node 22; React 19). Every route is a server component tree fed by `progressnow/v1`; the client bundle contains only the interactive islands (D6). Caching uses Cache Components (`cacheComponents: true`): data reads are `'use cache'` functions tagged `content` (plus `routes`, `site`, and per-key tags such as `post:{lang}:{slug}` for future granularity), with a long `cacheLife` — freshness is **pushed** by the receiver (D9), not polled. `searchParams`-dependent fragments (search, `?category=`, `?paged=`, `?view=`) live inside `Suspense` so the static shell of a page is served from cache and only the dynamic fragment renders per request (partial prerendering). Manifest routes are pre-rendered at build (`generateStaticParams` from `/routes`, both languages) with `dynamicParams = true`, so content published after the build still resolves on first request.

*Fallback (decided up front):* if Cache Components proves unstable for this app, drop to the data cache only — tagged `fetch` + `revalidateTag`, pages dynamic — same architecture, same receiver, HTML rendered per request from cached JSON. The specs describe behavior, not the caching API, so either satisfies them.

*Alternatives:* `output: 'export'` rebuilt by the pipeline — rejected: no server rendering for search/filter/calendar states, and it recreates the rebuild-latency problem the Nuxt change spent D4–D7 on. Pure request-time SSR with no cache — rejected: every visitor would hit WordPress; ETag/transient caching on the WP side does not remove the network hop. Pages Router — rejected: no RSC, larger client bundle, no streaming.

### D2. Data layer: ported `api.ts`, server-only, contract-validated
`lib/api.ts` is ported from Nuxt with the same semantics: one function per endpoint, `validate(schema, data)` throws in dev and logs + throws `ApiError('progressnow_contract')` in prod so the route renders the honest error state (`error.tsx`) rather than wrong data. The module is `import 'server-only'`; `WP_API_BASE` is a server-only env var — the browser never learns the WordPress origin's API. Conditional requests (ETag) are not used: the Next cache is authoritative between revalidations and WordPress' own transient cache absorbs the misses. `zod` stays the runtime validator because the contract file is shared byte-for-byte with the theme (D7).

*Alternative:* a generated client from the fixtures — rejected: the zod file *is* the contract (contract-governance § Single contract definition).

### D3. Routing: one catch-all, the Nuxt resolver, Polylang owns URL structure
**Implementation notes (2026-09-05).** (1) One root layout (`app/layout.tsx`) for every route: a root layout placed inside the `[[...slug]]` segment remounts on each navigation and, under Cache Components' `<Activity>`, leaves the previous header/footer/`main` in the DOM hidden (duplicate landmarks, broken skip link). The layout learns the path from `x-pathname`, forwarded by `proxy.ts`, so it renders per request from the cached data layer — the trade-off already accepted for the nonce CSP (D11). (2) The chrome renders one persistent `<main id="main" tabIndex={-1}>`; route components render `div[data-route-kind]` inside it. (3) 404s are decided in `proxy.ts`: Cache Components always streams a fallback shell for a dynamic segment, so a page-level `notFound()` can only yield 200 + a client-rendered 404. The proxy keeps the `/routes` manifest in process memory (60 s TTL, at most one refresh per 10 s window on a miss — so newly published content resolves without a redeploy while bogus paths cost WordPress ≤ 1 request per window), renders the not-found route internally and answers with its server-rendered HTML and a real 404. The build no longer needs the API (no `generateStaticParams`).
`app/[[...slug]]/page.tsx` resolves `params.slug` + `searchParams` with the ported `resolveRoute(manifest, path, query)` and renders the matching `routes/Route*.tsx`. Language is derived by the resolver (longest front-route prefix), never by a locale middleware: `/es/…` paths exist because Polylang says so, and the app must not invent URLs WordPress does not have. The root layout reads the manifest (cached) to set `<html lang>` and `dir`, and fetches `/site?lang=` for the chrome. Trailing slashes are normalized the WordPress way (`trailingSlash: true`) so canonical paths match byte-for-byte across all three frontends. An unknown path renders `not-found.tsx` from the cached manifest — there is deliberately **no** live `/routes` re-read on a miss (the Nuxt app needed one because its manifest was frozen at build time; here the receiver invalidates `routes` on every content bump, and an unauthenticated miss must never cost an upstream request).

*Alternative:* `next-intl`/`[lang]` segment routing — rejected: duplicates Polylang's routing decisions and breaks parity when an editor renames a translated slug.

### D4. Links and media: re-home WordPress URLs at render
A `<SiteLink>` component (wrapping `next/link`) and a pure `toAppHref(url, wpOrigin)` helper apply the same rules as the Nuxt `links.ts`: a URL on the WordPress origin becomes a relative `pathname+search+hash` on the Next origin **unless** it is WordPress-only — `/wp-admin`, `/wp-login.php`, `/wp-json`, `/wp-content`, `/feed` (the ICS link-out), or a file extension — in which case it stays absolute; external URLs pass through with `rel="noopener"`. `wpOrigin` comes from `/site.homeUrl`. Images: slot images with known dimensions (cards, hero, teasers, gallery) use `next/image` with `remotePatterns` for the WordPress uploads host; in-content HTML (kses'd blocks) keeps WordPress' own `srcset` via plain `<img>` — `next/image` cannot see inside an HTML string and WordPress already sized those. The theme's `static/` (fonts, brand placeholders) is exposed same-origin through a `rewrites()` proxy of `/wp-content/themes/progressnow/static/:path*` → `WP_ORIGIN` with immutable cache headers, because `@font-face` is CORS-gated and the operator may not control WordPress' headers; this also keeps `tailwind.css` byte-identical to the theme (D7).

*Alternative:* self-hosting font copies via `next/font/local` — viable, cleaner preload semantics, but adds a second drift surface (binary files) and breaks CSS identity; kept as the documented escape hatch if the proxy is undesirable.

### D5. SEO: envelope-driven metadata, and one configurable canonical origin on the PHP side
`generateMetadata` maps the envelope's `seo` block 1:1: `title`, `description`, `robots`, `alternates.canonical`, `alternates.languages` from `hreflang`, Open Graph `url` = canonical and image from the route's image or `identity.share_image`; `styleguide` is forced `noindex` regardless. `app/sitemap.ts` and `app/robots.ts` are generated from `/routes` (both languages, canonical origin). The canonical **value** is not rewritten by Next. Instead `inc/seo.php` gains `progressnow_seo_public_url( $url )`, applied inside `progressnow_seo_canonical()`, `progressnow_seo_hreflang()`, and `og:url`, which swaps the URL's origin for `CHAPTER_CANONICAL_ORIGIN` (wp-config constant or `progressnow/seo/canonical_origin` filter; default = `home_url()` origin, i.e. a no-op). Because the Twig `<head>` and the REST `seo` block share these functions, the PHP theme, the Nuxt app, and the Next app agree on canonical by construction, and an install that makes Next primary sets one constant. The same helper is applied to WordPress core sitemap entries (`wp_sitemaps_*_entry` filters) so the core sitemap never lists non-canonical URLs. Fixtures for envelopes with a canonical gain the origin-swapped variant in `tests/test-seo.php`.

*Alternative:* Next rewrites canonical/hreflang hosts client-side — rejected: the PHP theme's own pages would still self-canonicalize and the two frontends would compete for the same content.

### D6. Interactivity boundaries and state
Server components render all content and chrome. Client components ("islands", `'use client'`) are limited to: `SiteHeader` mobile nav + menus, `LanguageToggle` (receives the current route's `languages` as props — the Nuxt "SiteHeader stays mounted, refresh a store" hack disappears because every route renders its chrome with its own translations), `A11yWidget` + `A11yProvider`, `BlogArchiveControls`, `EventCalendar`, and shadcn overlays. No global store library: server data arrives as props; URL is the state for search/filter/page/view; the a11y settings are a React context backed by `localStorage` (`chapter-a11y`, legacy migration preserved) applied as `data-text-size|data-contrast|data-motion` attributes on `<html>` by a nonce'd inline script in the root layout **before** first paint (no flash), then owned by the provider.

**Blog archive.** Typing/choosing writes `?s=`, `?category=`, `?paged=` with `router.replace(…, { scroll: false })` debounced 300 ms; the results fragment is a server component reading `searchParams` inside `Suspense`, rendered with `useTransition` pending state and `aria-busy`; superseded transitions are dropped by React. Browse mode (no query, "All") renders the embedded first page and featured card with no fetch. Search results are cached per query with a short `cacheLife` and stay `noindex` (already in the envelope).

**Calendar.** The calendar page fetches the events envelope server-side and passes it to the client `EventCalendar`; month navigation and month/list view (`?view=list`) are client state over that window; a window outside the loaded range is fetched from the same-origin route handler `GET /api/events?lang&from&to`, which is itself a tagged cache read. Skeleton and `role="status"` semantics match the Nuxt component.

**Navigation and view transitions (decided).** Route changes cross-fade using the View Transitions API through Next's view-transition support (`experimental.viewTransition`, React `<ViewTransition>` around the route slot). The transition is skipped when `prefers-reduced-motion: reduce` is set or the widget's reduce-motion setting is on, and degrades to an instant swap where `document.startViewTransition` is missing — progressive enhancement, never a dependency. URL-state updates (search, filter, page, view) are `router.replace` with `scroll: false` and do not trigger a transition.

*Alternative:* client-fetched search like the islands — rejected: the user asked for SSR search; URL-driven server rendering also gives shareable URLs, back/forward, and no browser→WP path. Shipping without cross-fade in v1 — rejected by the user; the reduced-motion and unsupported-browser paths keep it safe.

### D7. Design system: shared by drift test, components re-implemented
`next-js/app/globals.css` is the theme's `src/css/tailwind.css`, byte-identical after the same normalization the Nuxt drift test applies (font/asset URL prefix; app-only `@source` block). `lib/schemas.ts` and `categories.json` are byte-identical copies. `test/unit/shared-source-drift.test.ts` fails on any drift — the theme stays the source of truth; edit there, re-copy here. Tailwind v4 via `@tailwindcss/postcss` (no config file; `@theme` in CSS). shadcn/ui (`new-york`, `neutral`, CSS variables, lucide-react) is installed component-by-component, only what the site components use (accordion, alert-dialog, aspect-ratio, badge, breadcrumb, button, calendar, card, carousel, collapsible, command, dialog, popover, separator, sheet, tooltip …); the `--radius` scale (20/14/999), `data-tone="blue|white|alt|ink"` bands, high-contrast token swaps, and the role-named palette (`brand`, `accent`, `alt`, `ink`, `--color-cat-*`) come from the shared CSS untouched. Site components (`components/site/**`) are React re-implementations of the Vue twins with the same section structure and class literals where practical — the Styleguide route (`/styleguide/`, `noindex`) is the visual-parity surface and the first e2e/axe target. **Kitchen sink (user decision 2026-09-05):** the styleguide is also a visual guide to the whole shadcn/ui library on the chapter tokens — every registry `ui` component is installed and shown through its canonical registry `*-example` (`components/styleguide/examples/`), grouped like the Nuxt styleguide (brand tokens → form controls → overlays & navigation → data & complex), each section anchored and axe-scanned in every a11y mode. Installing the full set does not touch the front page's budget: routes are code-split and only the styleguide imports the sink. The `useA11ySettings` behavior (keys, shape, migration, font sizes 16/18/20 px) is re-implemented with its own unit tests mirroring the Vue composable's.

*Alternative:* extracting a `packages/contracts` workspace — deferred: three consumers with one byte-identical file and a test is simpler than a monorepo toolchain the PHP theme cannot use.

### D8. Accessibility contract
- Landmarks: one `<header>`, `<nav aria-label>` per nav, `<main id="main" tabIndex={-1}>`, `<footer>`; skip link (`strings.skip_link`) first in DOM.
- Navigation: on route change focus moves to `<main>` (not the top of the document) and the page title is announced — Next's built-in route announcer is relied on and asserted in e2e; scroll to top or to `#hash`; `prefers-reduced-motion` and the widget's reduce-motion disable view transitions and non-essential animation (`tw-animate-css` gated).
- Widget parity: text size (`html { font-size }`), high contrast (`data-tone` swaps), reduce motion; persisted; announced changes via `role="status"`.
- Interactions: calendar month grid is a `grid` with `aria-label`ed cells, arrow-key navigation, `aria-live="polite"` month heading, `aria-pressed` view toggle; archive controls use a labelled `search` input with `aria-busy`/`role="status"` results count; dialogs trap and restore focus (Radix); menus close on Escape; every icon-only control has a name.
- Content: kses'd HTML is rendered via `dangerouslySetInnerHTML` with the same trust boundary as `v-html`; heading order is preserved by the block renderer; images from envelopes carry their `alt` (empty `alt` for decorative art such as `cta-panel.svg`).
- Acceptance — **axe-core is the single a11y engine, and it runs against the built app.** A dedicated `test:a11y` gate starts the production build (`next build && next start` against the mock API) and runs `axe-core` (via `@axe-core/playwright`, pinned to one `axe-core` version) on every route kind × language × widget mode (default, high contrast, xl text, reduce motion) and on each interactive state that changes the DOM (mobile nav open, a11y popover open, calendar list view, archive with a search query, event dialog open), with the rule set `wcag2a, wcag2aa, wcag21aa, wcag22aa` plus `best-practice` (best-practice violations are warnings for the first two milestones, then errors). Zero violations is the pass bar; results are written as JSON artifacts per page so a failure names the rule, selector, and route. The same engine runs at component level (`jest-axe`, which wraps `axe-core`) in Vitest, and optionally in the dev server (`@axe-core/react` behind `NEXT_PUBLIC_AXE=1`) so authors see violations in the console while building. `eslint-plugin-jsx-a11y` (strict) is the static layer; it does not substitute for the axe-core gate.

### D9. Revalidation receiver
`POST /api/rebuild` (route handler, Node runtime): reads the raw body (≤16 KB), requires `X-Chapter-Timestamp` (9–11 digits, |now − ts| ≤ 300 s) and `X-Chapter-Signature` (`sha256=` + hex HMAC-SHA256 of `${timestamp}.${body}` with `CHAPTER_REBUILD_SECRET`), compares with `crypto.timingSafeEqual`, rejects a repeated `(timestamp, signature)` within the window (in-memory LRU; across instances the operation is idempotent so a replay is harmless). On success it calls `revalidateTag` for `content`, `routes`, `site`, and responds `202 { buildId: <uuid>, status: "started" }` — exactly what `progressnow_rebuild_send_webhook()` expects — then, when `WP_BUILD_STATUS_URL` is configured, posts a signed `{ buildId, status: "succeeded", contentVersion }` to `/progressnow/v1/build-status` so WordPress marks the build live, purges its page cache, and the admin "Site build" panel reflects Next builds. Failures answer 401 (signature), 400 (shape), 413 (size), never 5xx for bad input; all are logged with the `requestId`. `GET /api/health` returns `{ ok, buildId }` without touching WordPress. The receiver is unit-tested with vectors generated by the PHP signing scheme (`progressnow_rebuild_sign` semantics reproduced in the test).

*Alternative:* polling `/routes.contentVersion` on an interval — rejected: adds constant upstream load and a freshness lag for every install; kept only as a documented manual fallback (`revalidate` via the health route with the secret) for operators using `CHAPTER_REBUILD_TRANSPORT=none`.

### D10. Test harness and mock API
- **Unit (Vitest, node env):** resolver, `toAppHref`, `api.ts` validation modes, receiver signing/replay, a11y settings store, metadata mapping, sitemap.
- **Component (Vitest + jsdom + RTL + jest-dom + user-event + jest-axe):** every `components/site/**` component against fixture props, including keyboard paths.
- **Contracts:** the theme's `tests/fixtures/*.json` parsed by `lib/schemas.ts` (the Nuxt `contracts.spec.ts` ported) and the drift tests (D7).
- **E2E (Playwright):** `next build && next start` with `WP_API_BASE` pointed at a standalone fixture-backed mock server (`test/mock/server.mjs`, the Nuxt `shared/mock-api.ts` ported — same overlays, same `MOCK_CONTENT_VERSION`), covering every route kind × `en|es`, the archive and calendar interactions, the a11y widget, the 404, and the receiver round-trip (signed POST → content changes on next request). The mock server is not part of the production bundle (unlike the nitro mock route).
- **A11y gate (`test:a11y`, axe-core against the build):** a separate Playwright project that reuses the same built server and runs `axe-core` per D8 over the route × language × mode × state matrix, emitting per-page JSON reports and failing CI on any violation. Kept separate from the functional e2e so an a11y regression is reported as such, and so the matrix can grow without slowing the functional suite.
- **Unit-level RSC:** server components are tested as async functions returning trees where practical; route-level behavior is owned by e2e.
- **TDD rule:** each task in `tasks.md` names the test(s) it lands first; CI runs `lint`, `typecheck`, `test:unit`, `build`, `test:e2e`, `test:a11y` (the last two against the same built server).

### D11. Deployment and hardening
`output: 'standalone'`, multi-stage Dockerfile (non-root, `HOSTNAME=0.0.0.0`, `PORT`), health route, `poweredByHeader: false`. Env contract: `WP_API_BASE` (server), `WP_ORIGIN` (derived unless set), `NEXT_PUBLIC_SITE_ORIGIN` (sitemap/OG absolute URLs), `CHAPTER_REBUILD_SECRET`, `WP_BUILD_STATUS_URL` (optional), `IMAGE_HOSTS` (remote patterns), `MOCK_API=1` (dev/e2e). Security headers and a nonce-based CSP (`script-src 'self' 'nonce-…' 'strict-dynamic'`, `img-src 'self' data: <uploads host>`, `font-src 'self'`, `frame-ancestors 'none'`) are set in the request proxy; the a11y bootstrap script and Next's own inline scripts use the nonce. **Decided 2026-09-05:** a per-request nonce means HTML renders per request (the cached data layer still absorbs WordPress), giving up the prerendered static shell in exchange for a real script CSP; hash-based CSP cannot cover RSC's inline payload scripts and needs nothing from WordPress either way. Measured TTFB is checked in task 8.1 and the CSP is rolled out report-only first. Cache handling: single instance or Vercel in v1; the `cacheHandler` seam for multi-instance (Redis) is documented, not shipped. `docs/deployment.md` gains "Headless Next.js" (Vercel, Docker, VPS + reverse proxy, WordPress constants: `CHAPTER_REBUILD_TRANSPORT=webhook`, `CHAPTER_REBUILD_WEBHOOK_URL=<origin>/api/rebuild`, `CHAPTER_REBUILD_SECRET`, `CHAPTER_CANONICAL_ORIGIN`).

### D12. Rename `site/` → `nuxt-js/` and repository docs
A single mechanical commit: `git mv site nuxt-js`, then update `README.md`, `docs/deployment.md`, `bin/worktree-bootstrap.sh`, the `nuxt4-static-platform` change docs, and any workflow files. The root README is rewritten around "one CMS, three frontends": PHP theme (server-rendered, no Node), `nuxt-js` (static rendition + PHP shell handoff), `next-js` (headless, Node-hosted) — with the per-install decision table (rebuild transport, canonical origin, static dir) and pointers to each app's README.

## Risks / Trade-offs

- [Cache Components / PPR API churn across Next minors] → pin the major, wrap cache reads behind `lib/data/*` so the fallback (D1) is a local change; specs describe behavior only.
- [Cross-origin fonts and brand assets] → same-origin rewrite proxy (D4); documented self-host alternative.
- [Per-keystroke search load] → 300 ms debounce, transitions supersede, short-lived per-query cache, WordPress transient cache; search stays `noindex`.
- [Multi-instance cache incoherence] → v1 targets one instance or Vercel; document `cacheHandler`; the receiver is idempotent so every instance can be hit.
- [Editor latency ≈ dispatcher debounce (90 s)] → "Rebuild now" and WP-CLI dispatch synchronously; acceptable for autosave-triggered bumps.
- [Two frontends, duplicate content] → `CHAPTER_CANONICAL_ORIGIN` (D5) + sitemap only on the canonical origin; whether the PHP theme should also `noindex` when it is not primary is deferred (Open Questions).
- [kses'd HTML in React] → same boundary as `v-html`; CSP nonce backstop; no inline scripts allowed by policy.
- [Drift tests couple to the theme path] → same as Nuxt; CI checks out the monorepo; documented.
- [Visual parity without pixel diffs] → styleguide route + per-route screenshots as review artifacts; pixel diffs are an opt-in follow-up.
- [Next view-transition support is experimental] → isolated to one wrapper component; feature-flagged; e2e asserts both the animated and the reduced-motion paths so removing the flag is a one-line change.
- [Client bundle growth from shadcn/Radix] → islands only (D6); bundle budget asserted in CI (`next build` size output checked against a threshold). **Learned 2026-09-05 (task 6.6):** with a single `[[...slug]]` page, every client component statically imported by any route lands in the page's shared chunks, so the front page pays for the calendar island; `next/dynamic` called from a server component did not split it under Turbopack. The working split point is a dynamic `import()` inside the client graph (`CalendarIsland.tsx`: a tiny `"use client"` wrapper with `React.lazy` + `Suspense`, still server-rendered). Use that pattern for any further route-specific island of size.
- [Upstream failure → honest 500] **Learned 2026-09-05 (tasks 6.8/7.1):** three facts shape the error path. (1) Errors must never cross a `'use cache'` boundary: in production they reach the caller *obfuscated* (a plain `Error` carrying only Next's `digest`), `instanceof` is false across Next's separate bundles (cache scope, route handler, proxy), and when several callers share one in-flight fill the leader's error is rethrown into the render itself — past every `try/catch` (observed once `generateMetadata` joined the layout and page as a caller) — aborting the response into Next's bare 500. So `lib/data` cached scopes return a `Result`, mark a failed result non-cacheable (`cacheLife({stale:0,revalidate:0,expire:0})`), and the public getters throw `UpstreamError` OUTSIDE the scope; the API layer logs the specific cause (`upstream_failure` / `upstream_contract`). (2) Render code must not read the clock: `Date.now()`/`new Date()` during the prerender pass is a fatal "unstable value" — so digests are clock-free and render-time logging is deferred with `after()`; `HANGING_PROMISE_REJECTION` (the prerender pass aborting a pending cached read) is rethrown, never treated as a failure. (3) A layout cannot set a status and a throw from the concurrently rendering page (or metadata) aborts the whole response, so `app/layout.tsx`, `app/[[...slug]]/page.tsx` and `generateMetadata` never throw on data failure (they render the server-side error document / surface, or empty metadata), and `proxy.ts` answers the real **500** — when its manifest probe fails, or when the process-local upstream-health signal (`globalThis`, shared across bundles in the standalone deployment) says the data layer just failed and a fresh probe confirms it — by rendering `/_error-route/` internally with `x-error-render` (same mechanism as the 404). The first failing request in a process may still stream the surface with a 200; every one after is a 500 until a probe succeeds, at which point recovery is immediate. The `failure` Playwright project runs this scenario serially after `e2e` and `a11y` because it flips the mock for every envelope.
- [Hardcoded copy sneaking in] → components accept `strings` props; e2e runs in `es` and fails on English fallbacks for known keys.
- [Receiver exposed publicly] → constant-time HMAC, replay window, size cap, no upstream call on failure; rate limiting left to the host/edge and documented.
